# Candidate and qualification reference

Shared private prototypes are registered once in `PRIVATE_CANDIDATES` in `scripts/run_benchmark.py`: validator/producer module, report key, and whether a settled observation is required. The parser, launch hooks and common observation lifecycle use that definition. Modules retain their exact input admission, staging, activation, source/work validation and assessment. Specialized routes outside this lifecycle retain their existing handlers.

Shared private runs use one atomic selection/source-observation reload per arm under an explicit `privateObservedReload` launch capability, with master Off, empty requests/options, actual dimension and archive-byte checks. Observers are disarmed before capture; the source/physical validators and native options remain required. Frozen Bliss qualification retains its separate launch gate and schedule. Historical multi-reload results remain separate evidence.

For the separately authorized frozen Bliss AO qualification, `test --candidate n04-bliss-sky --scene saved --saved-pose 0|7 --bliss-qualification null|clock|ao --qualification-order ABBA|BAAB` selects a maintained four-window block. A is the original; B is a byte-identical original ZIP alias for `null`/`clock`, or the existing AO candidate for `ao`. Current `atomic-observed-reload-v3` arms actual-source observation before the verified selected-pack reload in one owned action. Every arm drains prior GL work during untimed setup, then performs one successful-path reload; a failed reload disarms observation before rollback. This is a resource-peak experiment, not demonstrated memory reclamation. The earlier two-reload cohorts remain separate evidence. Timing is 60 seconds per window after 20 seconds settling, with initial 180-second conditioning and an 1800-second recovery-inclusive budget. Work counters are disabled; complete observer status must remain false at both timing boundaries. Strict checks reconcile contiguous single-epoch raw samples, render/world-entry counts, duration and returned-render timestamps. Start/render/end duration reconciliation permits a fixed 5ms difference between first/last endpoint bookkeeping. This measures total-frame start intervals, not GPU completion. `clock` declares a 25ms render-thread spin in B only; CPU/GPU overlap can hide some of that added CPU work in total throughput, so it is an instrument check, not an optimization or bandwidth result.

The bounded calibration and decision rules are frozen before runtime in `dev/experiments/benchmark-trust-bliss-20261103/preregistered-plan.json`: two clock blocks, then six fresh-process null blocks per scene with balanced orders; AO is gated on both scenes calibrating. All valid losses and invalid attempts remain recorded. `python3 scripts/benchmark_bliss_qualification.py --mode null|ao --runs /path/to/attempt ... --output /path/to/fresh/cohort.json` evaluates complete cohorts; AO additionally requires `--calibration /path/to/passing-null-cohort.json`. Uncertainty uses process blocks rather than individual frames, and remains approximate/session-specific. Single-block reports deliberately issue no performance qualification verdict. This protocol does not change prior goal dispositions or grant public/default, visual, DH/PBR or hardware-wide qualification.

The initial twelve-block Bliss null cohort failed calibration in both scenes; valid execution did not establish stable measurements. Both bounded repair cohorts remain incomplete after owned kernel OOM kills; v3 also contains a same-treatment spread above the original limit. The excluded capacity diagnostic is not a passing null cohort. See `dev/experiments/benchmark-trust-bliss-20261103/final-interpretation.json`; AO timing remains blocked. The prospective Linux memory-budget variant adds `--qualification-client-heap 1536m` (2304m is also explicitly supported). This changes only the owned client’s launch property, retains the existing Gradle budget and native shader quality, and verifies the effective JVM maximum before conditioning and at capture boundaries. Heap maximum/committed/used values and relevant JVM arguments are exported. Read-only host pressure/swap counters and client faults/RSS are sampled outside scored intervals; their external brackets include controller/export endpoints and do not isolate GPU or client causes. Source/runtime signatures prevent mixing heaps or instrumentation variants within a cohort or between passing null and AO cohorts. The separately frozen `preregistered-memory-repair-v2.json` defines one diagnostic and one replacement null cohort with unchanged acceptance gates. Swap occupancy, later quiet-host snapshots and a lower requested heap do not by themselves prove active swapping, reduced residency or the cause of prior stalls.

For the new CPU qualification work, `--features quad_command_compaction,shadow_admission_cache` (optionally adding `index_scalar_cache`) tests only those CPU requests on the pinned original archive, retaining the exact complete native option map. Compaction requires the admission cache. The test requires actual returned compaction batches, scalar hits when requested, and admission-cache progress captured at the timing boundaries before later status queries. Command-entry counts are not GL draw counts; execution without fewer entries remains a valid outcome. Normal master Off/On Apply may reload the native pipeline; record that transition and require stable pipeline/terrain-program identities within each timing interval. Setup reload cost is reported separately, so steady-state timing does not establish amortized net benefit. Current CPU subset tests do not admit DH.

For native CPU standard comparisons on Linux without DH, optional `--cpu-placement` records read-only `sched_getcpu` samples at each renderer boundary and prelaunch CPU cluster topology. The default is off. Boundary histograms do not measure residence, per-core CPU time or causation; migration that returns to the same CPU is invisible and observer overhead is uncalibrated. The observer does not change affinity or governors. Keep the usual command/cache-work, graph identity, exact native options and restoration requirements.

Optional `--render-cpu 4 --cpu-placement` declares a controlled Linux CPU diagnostic for those same CPU comparisons. It pins only the calling render thread during each settled timed capture and verifies the original CPU mask is restored before the next reload or observation. Existing threads retain their masks; a detected surviving new thread inheriting the temporary restricted mask invalidates the run and the owned client stops. This endpoint census does not detect transient children that exited before the final scan. Every recorded head/tail boundary must match the declared CPU, without unknown samples or migration. The default is disabled. No governor or global settings change is made. This diagnoses cluster scheduling effects; it does not qualify ordinary scheduling, fixed CPU frequency or general performance.

`--untimed-diagnostic cpu-admission-cost` requires the exact public CPU triple `--features quad_command_compaction,shadow_admission_cache,index_scalar_cache`, no DH, and a standard test. It observes at least128 completed frames after candidate timing, at the actual consumer checks and compactor/scalar bodies, inclusive native fill/maximum-query scopes, and nonshadow native submission delegate. It also measures4096 empty clock pairs once when arming. Nested/inclusive intervals must not be summed; scalar lifecycle includes eligible enter/finish plus all clear-site begin-selection callbacks, so it cannot be subtracted from fill. Native submission is CPU delegate-chain time, not GPU completion or isolated driver work. Clock aggregates include observer overhead; empty calibration is contextual and must not be blindly subtracted. Clock reads are disarmed in scored windows, while ordinary plans disable the diagnostic branch. Own-JVM DH-permission transitions test cache invalidation and restore every property; without DH installed they do not qualify live-DH admission. No consumer permission is reused or safety guard removed.

If the harness or inputs fail, preserve the failure, restore/release owned resources, fix the maintained harness or inputs, and retry. Do not copy harness code into report-local callers, inject launcher overrides, relax admission after failure, or substitute custom scripts for the standard result. Diagnostics are diagnostic and do not replace it. One Linux ARM64 BSL standard run completed with verified restoration and independent review; this does not establish behavior for other configurations or future changes. See [experiment history](EXPERIMENTS.md).

Keep reports, worlds, downloads, builds and captures out of Git. Do not kill unrelated processes. If restoration refuses due to unknown changes, preserve the data and inspect ownership and recovery before acting.

Runtime dependencies and original shader-pack inputs are stored under `dependencies/`. Keep active experiment output in `dev/experiments/` and any retained evidence in `experiment-evidence/`; both are local and outside Git. Prepared clients and worlds remain under `run-workloads/`.
